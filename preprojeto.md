RNFs (Requisitos Não Funcionais)

**Críticos (essenciais para o produto funcionar com confiança)**  
**O sistema deve garantir que nenhum dado do usuário seja perdido (durabilidade de dados)**

1. O sistema deve salvar automaticamente sem perda de progresso em caso de queda de conexão  
2. O sistema deve criptografar dados sensíveis em trânsito (HTTPS/TLS)  
3. O sistema deve criptografar dados sensíveis em repouso (banco de dados)  
4. O sistema deve realizar backup periódico automático dos dados  
5. O sistema deve garantir isolamento de dados entre usuários/projetos (multi-tenancy seguro)  
6. O sistema deve estar disponível pelo menos 99,5% do tempo (uptime)  
7. O sistema deve validar e sanitizar todas as entradas para evitar injeção de código (SQL Injection, XSS)  
8. O sistema deve autenticar todas as requisições sensíveis via token seguro  
9. O sistema deve limitar tentativas de login para evitar ataques de força bruta  
10. O sistema deve permitir recuperação de dados em caso de falha catastrófica (disaster recovery)  
11. O sistema deve responder a ações críticas (salvar, editar) em menos de 1 segundo

**Altos (impactam diretamente experiência e confiança)**

1. O sistema deve suportar pelo menos X usuários simultâneos sem degradação perceptível de performance  
2. O sistema deve carregar a interface principal em menos de 3 segundos  
3. O sistema deve escalar horizontalmente conforme aumento de usuários/dados  
4. O sistema deve manter consistência dos dados em edição colaborativa em tempo real  
5. O sistema deve ser responsivo (funcionar bem em desktop, tablet e mobile)  
6. O sistema deve ser compatível com os principais navegadores (Chrome, Firefox, Safari, Edge)  
7. O sistema deve permitir uso funcional mesmo com internet instável (modo offline básico)  
8. O sistema deve seguir princípios de acessibilidade (WCAG) para leitores de tela e navegação por teclado  
9. O sistema deve possuir versionamento de API para evitar quebra de integrações existentes  
10. O sistema deve registrar logs de erro para diagnóstico rápido de falhas  
11. O sistema deve isolar falhas de módulos de IA sem derrubar o restante da aplicação  
12. O sistema deve processar tarefas pesadas (IA, importação em lote) de forma assíncrona sem travar a interface

**Médios (relevantes para qualidade e manutenção a longo prazo)**

1. O sistema deve ter código modular e testável (arquitetura desacoplada)  
2. O sistema deve possuir cobertura de testes automatizados nas funcionalidades críticas  
3. O sistema deve permitir deploy contínuo sem downtime perceptível  
4. O sistema deve manter documentação técnica atualizada da arquitetura  
5. O sistema deve seguir um design system consistente em toda a interface  
6. O sistema deve permitir customização de tema (claro/escuro) sem impacto de performance  
7. O sistema deve garantir que buscas retornem resultados relevantes em menos de 2 segundos  
8. O sistema deve suportar internacionalização (i18n) para múltiplos idiomas de interface  
9. O sistema deve monitorar uso de recursos (CPU, memória, armazenamento) com alertas automáticos  
10. O sistema deve permitir rollback rápido em caso de deploy com falha

O sistema deve seguir padrões de conformidade legal (LGPD/GDPR) para dados pessoais  
**Baixos (desejáveis, mas não bloqueantes)**

1. O sistema deve permitir customização visual avançada (ícones, cores, fontes) sem impacto em outras funcionalidades  
2. O sistema deve oferecer exportação de dados em múltiplos formatos com qualidade visual consistente  
3. O sistema deve manter compatibilidade retroativa com versões antigas de exportação/importação  
4. O sistema deve permitir integração futura com plugins de terceiros sem reescrita do núcleo  
5. O sistema deve otimizar uso de armazenamento (compressão de imagens, textos)  
6. O sistema deve oferecer sugestões de performance ao usuário (ex: "esta pasta está muito grande")

## **Principais Desafios do Projeto**

### **Desafios técnicos (IA e processamento de linguagem)**

**Precisão do reconhecimento de entidades (NER) em português e multilíngue** — reconhecer personagens, locais, objetos e eventos corretamente é difícil, principalmente com nomes fictícios/inventados que não existem em nenhum dataset de treinamento.

**Resolução de coreferência** — saber que "ele", "o velho guerreiro" e "Aldric" são a mesma pessoa no texto é um problema não trivial de NLP, especialmente em textos longos com muitos personagens.

**Detecção de contradições confiável** — diferenciar uma contradição real de uma intencional (narrador não confiável, elipse temporal, ambiguidade proposital) exige entendimento contextual profundo, não só comparação literal.

**Custo computacional da IA em escala** — rodar análise semântica, geração de resumo, detecção de contradição e simulação de causalidade em textos extensos (romances inteiros) pode ficar caro e lento se não for bem arquitetado (cache, processamento incremental).

**Manter grafo de conhecimento consistente e performático** — à medida que o universo cresce (milhares de entidades e relações), consultas e visualizações do grafo podem degradar em performance.

### **Desafios de produto e escopo**

**Escopo extremamente amplo** — o projeto cobre brainstorm, worldbuilding, gestão de equipe, engenharia de software, RH, pesquisa científica. Cada domínio tem público e fluxo de trabalho diferente; tentar atender todos pode diluir a experiência e atrasar o lançamento (risco clássico de "featuritis").

**Definição de MVP** — com centenas de RFs listados, decidir o que é essencial para uma primeira versão utilizável é um desafio de priorização, não técnico.

**Curva de aprendizado do usuário** — tantas funcionalidades avançadas (grafos, causalidade, sandbox, IA) podem intimidar um escritor que só quer organizar textos. A UX precisa esconder complexidade até que o usuário precise dela.

**Confiança na IA generativa** — sugestões automáticas erradas (fusão de entidades erradas, resumo impreciso, conexões falsas) podem frustrar o usuário e quebrar confiança no produto rapidamente.

### **Desafios de dados e modelagem**

**Modelar um grafo genérico o suficiente para lore, RH, engenharia e pesquisa** — entidades, relações e regras de negócio são muito diferentes entre "personagem de história" e "funcionário de RH" ou "issue de engenharia". Um modelo de dados único que sirva bem a todos é difícil sem virar um sistema genérico demais (e por isso ruim em tudo).

**Versionamento de dados complexos** — histórico de versões, timelines paralelas, universos alternativos e sandbox "e se" multiplicam a complexidade de armazenar e comparar estados diferentes dos mesmos dados.

**Consistência em edição colaborativa em tempo real** — múltiplos usuários editando o mesmo texto ou grafo simultaneamente exige lidar com conflitos (CRDT ou OT), o que é complexo de implementar corretamente.

### **Desafios de infraestrutura**

**Custo de armazenamento e processamento de mídia** — imagens de capa, OCR, áudio (TTS), exportação de PDF ilustrado e mapas aumentam rapidamente o custo de storage e processamento.

**Escalabilidade multi-projeto e multi-usuário** — suportar múltiplos projetos, equipes, permissões granulares e colaboração em tempo real exige arquitetura robusta desde o início; retrabalhar isso depois é caro.

**Segurança e conformidade** — dados de RH e folha de pagamento têm exigências legais sérias (LGPD, sigilo salarial, auditoria), bem diferentes das exigências de um app de brainstorm criativo — misturar os dois no mesmo produto aumenta a superfície de risco legal.

### **Desafios de negócio**

**Público-alvo difuso** — escritores, times de engenharia, RH e pesquisadores raramente compram a mesma ferramenta. Definir para quem o produto é primeiro (e quem vem depois) é decisão estratégica antes de ser técnica.

**Monetização e precificação** — funcionalidades de IA têm custo variável por uso; precificar de forma sustentável sem inviabilizar usuários casuais é um desafio real.

**Concorrência estabelecida** — já existem players fortes em cada nicho (World Anvil/Campfire para lore, Notion/Jira para engenharia, Obsidian para PKM, Gusto/ADP para RH). Competir exige um diferencial muito claro em pelo menos um nicho antes de expandir.
